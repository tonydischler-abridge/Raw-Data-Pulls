# Ambient Detection Logic

> This document describes the four-method ambient detection pattern shared across all time-filtered raw queries. The same CTE block appears in every fact query: Encounter, Transaction, Diagnosis, Notes, Schedule, Activity, and CDI.

---

## Overview

Abridge encounter detection is not a single signal — it is derived from **four independent detection paths** that reflect how different Epic configurations store ambient AI session data. The CTEs are UNIONed together, meaning an encounter only needs to match **one** of the four methods to receive `AMBIENT_FLAG = 'Y'`.

```sql
ALL_AMBIENT AS (
    SELECT PAT_ENC_CSN_ID FROM AMBIENT_VIA_SDE
    UNION
    SELECT PAT_ENC_CSN_ID FROM AMBIENT_VIA_NAS
    UNION
    SELECT PAT_ENC_CSN_ID FROM AMBIENT_VIA_ATTR
    UNION
    SELECT PAT_ENC_CSN_ID FROM AMBIENT_VIA_DXR
)
```

---

## Method 1: SmartData Elements (AMBIENT_VIA_SDE)

**Tables:** `SMRTDTA_ELEM_DATA`, `SMRTDTA_ELEM_VALUE`

```sql
AMBIENT_VIA_SDE AS (
    SELECT DISTINCT e.PAT_ENC_CSN_ID
    FROM date_filtered_enc e
    WHERE EXISTS (
        SELECT 1
        FROM SMRTDTA_ELEM_DATA sde
        INNER JOIN SMRTDTA_ELEM_VALUE sev
            ON sev.HLV_ID = sde.HLV_ID
        WHERE sde.CONTACT_SERIAL_NUM = e.PAT_ENC_CSN_ID
            AND sde.ELEMENT_ID IN (
                'EPIC#31000231848',
                'EPIC#31000231852',
                'EPIC#31000231850',
                'EPIC#31000231851',
                'EPIC#31000231856'
            )
    )
)
```

**How it works:** Epic stores structured ambient session metadata as SmartData Elements (SDEs) on the encounter. These five element IDs correspond to Abridge-specific data points (session status, recording identifiers, etc.) that Epic populates when an Abridge ambient session is associated with the encounter.

**When this fires:** Most reliable for encounters where the ambient session was fully completed and written back to the encounter record via SDE.

**Dictionary references:**
- `SMRTDTA_ELEM_DATA` — Chronicles INI: EPT. Stores the SmartData element data for a record. `CONTACT_SERIAL_NUM` links to the encounter CSN.
- `SMRTDTA_ELEM_VALUE` — Linked via `HLV_ID`. Stores the actual values for each SDE line.

**Partner Note:** The specific Element IDs (`EPIC#31000231848` etc.) are Epic-standard identifiers for Abridge's integration. These should be consistent across Epic environments but confirm with Abridge Implementation if detection seems low.

## Method 2: Note Ambient Sections (AMBIENT_VIA_NAS)

**Tables:** `HNO_INFO`, `NOTE_AMBIENT_SECTIONS`

```sql
AMBIENT_VIA_NAS AS (
    SELECT DISTINCT e.PAT_ENC_CSN_ID
    FROM date_filtered_enc e
    WHERE EXISTS (
        SELECT 1
        FROM HNO_INFO hno
        INNER JOIN NOTE_AMBIENT_SECTIONS nas
            ON nas.NOTE_ID = hno.NOTE_ID
        WHERE hno.PAT_ENC_CSN_ID = e.PAT_ENC_CSN_ID
            AND nas.AMBIENT_SESSION_IDENT IS NOT NULL
    )
)
```

**How it works:** When an ambient AI session generates a note, Epic stores the session identifier in the `NOTE_AMBIENT_SECTIONS` table linked to the note (`HNO_INFO`). If any note on the encounter has a non-null `AMBIENT_SESSION_IDENT`, the encounter is flagged.

**When this fires:** When the ambient session produced a note that was filed to the encounter. Will not fire if the session ran but no note was generated or saved.

**Dictionary references:**
- `HNO_INFO` — Chronicles INI: HNO. One record per clinical note. Links to encounter via `PAT_ENC_CSN_ID`.
- `NOTE_AMBIENT_SECTIONS` — Stores sections of notes generated by ambient AI. `AMBIENT_SESSION_IDENT` is populated when the note section originated from an ambient AI session.

## Method 3: Note Attribution Source (AMBIENT_VIA_ATTR)

**Tables:** `HNO_INFO`, `NOTE_ATTRIBUTION`

```sql
AMBIENT_VIA_ATTR AS (
    SELECT DISTINCT e.PAT_ENC_CSN_ID
    FROM date_filtered_enc e
    WHERE EXISTS (
        SELECT 1
        FROM HNO_INFO hno
        INNER JOIN NOTE_ATTRIBUTION na
            ON na.NOTE_ID = hno.NOTE_ID
        WHERE hno.PAT_ENC_CSN_ID = e.PAT_ENC_CSN_ID
            AND na.NOTEATTR_SOURCE_C = 25
    )
)
```

**How it works:** `NOTE_ATTRIBUTION` tracks how each portion of a note was authored — manual typing, SmartText, voice recognition, ambient listening, etc. Source code `25` corresponds to "Ambient Listening" (i.e., Abridge). If any attribution record on the encounter's notes is source 25, the encounter is flagged.

**When this fires:** When the ambient AI contributed characters to a note that was fully attributed. Generally the most granular and reliable detection method for completed, filed notes.

**Dictionary references:**
- `NOTE_ATTRIBUTION` — Chronicles INI: HNO. Stores attribution records per note per LINE. Each line corresponds to a block of text attributed to a specific source.
- `NOTEATTR_SOURCE_C = 25` — Value 25 = "Ambient Listening." Defined in `ZC_NOTEATTR_SOURCE`.

**⚠️ Fan-out Warning:** `NOTE_ATTRIBUTION` has a composite PK of `(NOTE_ID, LINE)` — multiple rows per note. In `RawNotesPull`, the attribution join must handle this carefully to avoid duplicate note rows. See [RawNotesPull.md](RawNotesPull.md) for details.

## Method 4: Docs Received via DXR (AMBIENT_VIA_DXR)

**Tables:** `DOCS_RCVD_DETAILS`, `DOCS_RCVD_NOTE_SECTIONS`

```sql
AMBIENT_VIA_DXR AS (
    SELECT DISTINCT e.PAT_ENC_CSN_ID
    FROM date_filtered_enc e
    WHERE EXISTS (
        SELECT 1
        FROM DOCS_RCVD_DETAILS d
        INNER JOIN DOCS_RCVD_NOTE_SECTIONS n
            ON n.DOCUMENT_ID = d.DOCUMENT_ID
        WHERE d.DOCUMENT_RQST_CSN = e.PAT_ENC_CSN_ID
            AND d.DOCUMENT_RQST_CSN IS NOT NULL
    )
)
```

**How it works:** In some Epic configurations, ambient-generated documents are received via the document inbox (DXR module) and linked to the encounter via `DOCUMENT_RQST_CSN`. This method catches those cases where the ambient note was delivered as an inbound document rather than authored directly in the chart.

**When this fires:** Primarily in configurations where Abridge delivers completed notes as received documents to be reviewed and co-signed, rather than authored directly in Epic's note editor.

**Dictionary references:**
- `DOCS_RCVD_DETAILS` — Stores inbound received documents and their associated encounter CSN (`DOCUMENT_RQST_CSN`).
- `DOCS_RCVD_NOTE_SECTIONS` — Links received documents to note sections. Its presence confirms the document contained clinical note content.

**Partner Note:** This method may be less consistently populated than SDE or NAS depending on workflow configuration. If a partner has low detection rates, check whether their Abridge workflow routes through the DXR module.

## Detection Method Comparison

| Method | Fires When | Reliability | Key Table |
|---|---|---|---|
| SDE | Session metadata written to encounter | High — Epic-native integration | SMRTDTA_ELEM_DATA |
| NAS | Ambient session produced a note section | High — requires note filing | NOTE_AMBIENT_SECTIONS |
| ATTR | Note chars attributed to ambient AI (source 25) | High — most granular | NOTE_ATTRIBUTION |
| DXR | Note delivered as received document | Variable — depends on workflow | DOCS_RCVD_DETAILS |

## Common Questions

**Q: Can a single encounter trigger multiple methods?**
Yes. The UNION removes duplicates, so the encounter is counted once regardless. This is by design — UNION (not UNION ALL) ensures no double-counting.

**Q: What if Abridge detection rates seem low?**
- Confirm the SDE Element IDs match the partner's Epic build
- Check if the ambient workflow routes through DXR vs. native note authoring
- Verify that `ENC_TYPE_C` filter includes all relevant encounter types for that partner
- Confirm the go-live date in `DATE_PARAMS.START_DATE`

**Q: Should the physician-only filter (`PROVIDER_TYPE_C = '1'`) be applied before or after ambient detection?**
Ambient detection operates at the encounter level regardless of provider type — the flag indicates whether Abridge was used in the room, not who the provider was. The physician filter is more appropriate when aggregating metrics by provider (e.g., wRVU attribution) and should be applied in the BI layer or in downstream aggregated views.
